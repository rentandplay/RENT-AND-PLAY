# Page loading improvements

The previous navigation path invalidated the entire workspace cache on every page change. It also shared a single pending request between unrelated pages. Returning to a page therefore repeated the loading screen, and a slow request could hold up a different page.

The controller now keeps up to 24 in-memory snapshots keyed by the exact request, including date ranges, status, search and cursor. Fresh snapshots are reused for 30 seconds; older snapshots remain visible during background revalidation. Writes mark them stale, and sign-out clears snapshots and rejects late responses from the previous session.

After authentication, the active page has priority. One idle-time worker warms only Rates and Settings. History, customer directories, Payments, analytics, and equipment images are no longer all fetched automatically on sign-in. Sidebar hover/focus can still prefetch a destination, and a click shares its existing request.

Analytics date/category/equipment/grouping controls reuse the complete evidence snapshot. Reports already loads the full history because comparison periods, carryover rentals, in-period returns, and current overdue equipment use different date bases. Changing the selected period therefore recomputes from that history without downloading it again. Normal refresh, writes and sign-out still invalidate snapshots. Cash collections load when their disclosure opens and continue to use their own exact date range. Equipment reuses recent snapshots and refreshes after a save or explicit refresh.

Independent workspace database reads now start together. Settings and Rates skip unrelated rental/history collections. Named web workspace payloads omit equipment photo data; the inventory/detail endpoints continue to provide images. Audit and stock history preserve their saved public reference codes: dropping these codes previously caused reference enrichment to reread every log record, including records whose codes were already saved.

Unchanged page HTML is kept mounted, preserving chart interactions and avoiding redundant listener binding. React's development bundle rebuilds when source inputs change, and static assets support ETag revalidation instead of downloading unchanged files again. HTML and API responses retain their existing no-store behavior.

Supabase string equality and membership predicates now run in PostgreSQL through PostgREST. Matching rows are paginated by ID, including when the server enforces a smaller page cap. Unfiltered report history retains the aggregate RPC so it cannot be silently truncated at 1,000 rows. Simultaneous aggregate reads share one in-flight request, but completed authoritative reads are not cached. Successful writes detach any older pending reads. Installations exposing only the existing RPCs fall back without a schema migration.

Media hydration runs after scope, filters, ordering and pagination. A one-row proof query therefore downloads that row's image rather than every stored proof. Repeated reads inside one transaction attempt are shared, and retries start fresh. Saved rental, terminal and account reference codes also avoid redundant related-record reads.

Dashboard revenue reads start alongside stock reads. Read-only pages no longer wait for the expiry cleanup scan, and cleanup failures cannot independently take down a page. Booking, quoting, release and other stock-changing operations still validate authoritative records. Rental pricing and calendar checks overlap independent reads.

Once a rental commits, its response waits at most one second for derived report projection. A slow projection returns `summaryPending: true` with the successful rental; its existing durable report job and background task can complete afterward. Report caches are invalidated when the task finishes. This does not report an uncommitted booking as successful, and operation keys still prevent duplicates.

Timestamp formatters are reused rather than constructed per field. A local benchmark of 10,000 Manila timestamps decreased from 2,090 ms to 180 ms with the same output. This measures serialization only, not end-to-end live page latency.

The unavailable screen is a generic recovery message: HTTP 5xx errors, invalid responses, upstream dependency failures, and request timeouts can all lead to it. The web timeout is 20 seconds (30 seconds for Reports); Supabase requests have a 15-second deadline per upstream call. The screenshot alone cannot identify which dependency failed. Server failure logs now include the route, error code, elapsed time and diagnostic for both explicit upstream 5xx errors and unexpected failures. A healthy health check confirms connectivity at that moment, not every subsequent analytics or checkout request.

The Render blueprint specifies `plan: free`. If that is the active deployment plan, Render can spin down after 15 idle minutes and take about a minute to wake, independently of code speed: https://render.com/docs/free. No hosting-plan or production database changes were made as part of these code optimizations. The changes must be deployed before they affect the live site.

Verification covers bounded preloading, revisits without new requests, in-flight sharing, cross-page races, stale-content retention, save/sign-out invalidation, local analytics periods and filters, lazy cash queries, complete history above 1,000 rows, upstream page caps, write freshness, selective image hydration, stalled cleanup scans, deferred report projection, duplicate checkout retries, saved reference lookups and parallel dashboard reads. Full suites run with `npm test` in `apps/web` and `apps/backend`; HTTP tests need permission to connect to localhost. Use `node --test --test-concurrency=2 tests/*.test.mjs` for the web suite to avoid overloading timing-sensitive DOM tests.
